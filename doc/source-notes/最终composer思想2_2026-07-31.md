# 来源材料：最终Composer思想（第二份收紧反馈）

> 本文是形成Task 26设计的外部推理记录，不是规范。当前权威结论见
> [共享J语义物化与π约束Replay编译Agent最终设计](../IntentIR_共享J语义物化与pi约束Replay编译Agent最终设计_2026-07-31.md)。

我赞同：不需要为了“共享”再设计一套跨仓库接口。可以把后端已经验证过的 J materialization 逻辑选择性迁入 Replay，形成一个独立的 SemanticMaterializer Core。概念上与
  production 同源即可，工程上暂时不必强行共用同一个 API。

  另一个 Agent 的方案整体上更接近正确答案。尤其正确的是：

  - (S_J) 是只读编译器输入，不是目标代码模板；
  - Replay agent 是完整编译器，不是填洞器；
  - 不需要 per-node binding、固定 route assembler 或 fragment 拼装；
  - Agent 输出完整目标源码；
  - 最终忠实性仍由 Gate1/Gate2 判断。

  但有两个地方必须收紧，否则会与 π 的数学定位混淆。

  ## 正确的整体结构

  正常 Replay 应当是：

  [
  S_J=M(J)
  ]

  [
  R_f=A_f(J,S_J,\pi,\operatorname{MaskC}(C);U_f)
  ]

  由于 (S_J) 是 J 的确定性函数，它不是第四输入。严格地说，外部接口仍然只是：

  [
  W_f(J,\pi,\operatorname{MaskC}(C);U_f)
  ]

  内部工作流则是：

  exact J
    │
    └── deterministic SemanticMaterializer
              │
              ▼
         read-only S_J
         canonical typed semantic program

  π ───────────────────────────────┐
  MaskC(C) ────────────────────────┤
  U_f ─────────────────────────────┤
  exact J（只作权威回查）──────────┤
                                   ▼
                      fresh Replay Compiler Agent
                                   │
                                   ├─ 全局理解 S_J
                                   ├─ 全局理解 π
                                   ├─ 编写完整目标程序
                                   ├─ 编译并查看自己的 IR
                                   ├─ 自己重构和修复
                                   └─ 提交完整 Replay source

  宿主不再拼装最终源码，也不规定 Agent 必须逐节点映射。

  ## 可以直接把后端逻辑放进 Replay Core

  工程上可以这样做：

  python/intentir/verify/gate1/replay_semantic_core.py

  它从后端分支迁入并适配：

  - canonical J elaboration；
  - type/shape 推导；
  - operator/operand graph；
  - structured control；
  - domain、predicate、fill；
  - access/effect/output binding；
  - result relation；
  - typed boundary interpretation。

  但不要直接复制整个 backend/materialize.py，因为其中有：

  - concrete extent valuation；
  - constexpr specialization；
  - production loop form选择；
  - C attachment；
  - target/search state。

  Replay Core 要得到的是参数化、保留所有 J anchor 的 (S_J)，不是具体 production (M_0)。

  因此“复用后端工作”的准确含义是：

  > 复用它已经成熟的 J 解释和 boundary materialization 逻辑，放进 Replay 内部成为一个自包含 Core；不引入跨分支 API 工程，也不搬 production search、C 或 target
  > lowering。

  后面两个分支真正合并时再决定是否消除物理重复，不需要现在为代码复用增加复杂度。

  ## 另一个 Agent 有一点说得过宽：Replay 不能任意选择 lowering

  它说：

  > Replay agent自由选择 target lowering、融合、算法结构。

  这句话对 production backend 是正确的，但对 Replay 需要加上 π 约束。

  Production backend 的目标是：

  寻找任意满足 J 的高性能实现

  所以 production 不读取 π。

  Replay 的目标是：

  从 J 重建语义，并满足 π 所见证的 Source realization

  因此 Replay agent不是任意 optimizer，而是：

  > 一个由 (S_J) 提供语义、由 π 约束 realization、由 (U_f) 提供目标前端知识的完整编译器。

  它可以自由决定：

  - 目标语言语法；
  - API 拼写；
  - 临时变量；
  - pointer expression；
  - memory/layout 表达；
  - loop/carrier 的目标语言实现；
  - 同一 π realization 在目标前端中的工程组织；
  - 为满足编译器限制进行全局源码重构。

  但不能自由忽略：

  - π occurrence/multiplicity；
  - region/control；
  - physical iteration；
  - route/order/sharing；
  - carrier；
  - materialization；
  - terminal control。

  所以准确说法是：

  [
  R_f\in\operatorname{Realize}_f(S_J,\pi;U_f)
  ]

  而不是：

  [
  R_f\in\operatorname{AnyImplementation}_f(J)
  ]

  后者属于 production backend。

  ## 普通 softmax → online softmax 的例子要谨慎

  另一个 Agent 举例说：

  > (S_J) 表达普通 logical softmax，Agent 可以根据 π 编译成 online softmax。

  这个行为不是绝对不允许，但必须满足：

  - online update 的语义只能从 J/S_J 推导；
  - π 只提供 recurrence、carrier、region、route 等 realization 约束；
  - π 不能提供 max-update、rescale、sum-update 等算法公式；
  - Agent 不能把 π 当作隐藏的第二份 J。

  也就是说，Agent 可以像真正的编译器一样推导一个等价实现；但不能因为 π 看起来像 online-softmax 拓扑，就补造 J 中无法推出的算术。

  当前若 J 本身已经显式表达 recurrence，则最清楚；如果 J 只表达 extensional softmax，则 Replay agent承担的是一次真实算法 lowering，最后由 Gate1/Gate2裁决。两种都可能成
  立，但公式不能从 π 泄漏出来。

  ## “不可修改 S_J”的准确含义

  另一个 Agent 这一点是对的：

  - (S_J) 文件只读；
  - Agent 不修改它；
  - 最终源码不要求逐行保留 (S_J)；
  - 可以融合、分块、重排和重构；
  - Agent 输出的是对 (S_J) 的编译结果。

  这与普通编译器读取 AST/IR 一样。

  因此不需要通过结构化 hole 来保证“语义不能变”。现有 SCRC 本来就是生成后认证：

  - 只读 (S_J) 固定语义权威；
  - π 固定 realization 义务；
  - ReplayCheck 检查接口和构造；
  - Gate1 检查 Source–Replay realization；
  - Gate2 分别检查 Source–Replay、Source–J、Replay–J。

  我们不需要在 Replay 之前再建设一个形式化 verified compiler。

  ## π 应怎样提供给 Agent

  π 应由 Agent直接理解。宿主可以提供：

  - exact π 文件；
  - 按 region/instance/route 查询；
  - 将 semantic_ref 回指到 (S_J) 节点；
  - 局部邻接视图；
  - bounded graph/CFG 查询。

  这些都只是无损索引和查询。

  宿主不能：

  - 根据 π 生成 target skeleton；
  - 把 route 自动展开成源码；
  - 选择 loop/API；
  - 按 relation 类型生成 target statement；
  - 提供 Kernel 模板。

  所以现有 queryable π graph 可以保留；binding、block scaffold、fixed route renderer 应退出主路径。

  ## MaskJ 必须特别处理

  这是另一个方案没有强调、但非常重要的一点。

  正常轮：

  [
  S_J=M(J)
  ]

  MaskJ 消融轮必须是：

  [
  S_J^{mask}=M(\operatorname{MaskJ}(J))
  ]

  或者在 masked J 无法 materialize 时不提供完整 (S_J)。

  绝不能：

  先从完整 J 生成 S_J
  再只把 JSON J 做 Mask

  同理：

  - SemanticMaterializer 不读取 π；
  - 不读取真实 C；
  - 不读取 Harness valuation；
  - 不读取 Source/Gate；
  - masked episode 与 normal episode fresh、隔离。

  ## 最终裁决

  另一个 Agent 的主体判断是正确的，而且比我们此前的 hole/binding 设计好得多。最终架构应该是：

  - SemanticMaterializer Core：固定代码，直接消费 J，产生只读参数化 (S_J)；
  - Replay Compiler Agent：完整理解 (S_J+\pi)，自由编写完整目标源码，但 realization 必须满足 π；
  - π query tools：只做无损查询和回指，不生成目标结构；
  - compile/own-IR/checkpoint tools：帮助同一 Agent 完成真实编译循环；
  - 宿主不拼源码，不做 per-node binding，不维护 target recipe；
  - Gate1/Gate2 继续承担最终认证。

  唯一需要修正的措辞就是：

  > Replay agent不是“任意实现 J 的 production compiler”，而是“在 π 约束下编译 (S_J) 的完整 source-blind compiler”。

  ## 二、π 真的是 composer 生成的吗？

  是，代码证据非常明确。

  当前 Lift LLM 只能输出：

  J
  interface
  schedule
  strategy
  location_map

  如果 LLM 返回 plan 或 compose_provenance，直接拒绝。python/intentir/extraction/lifters/scrc.py:1190

  然后确定性代码执行：

  artifact, _ = materialize_replay_plan(artifact, registry)

  生成 π。python/intentir/extraction/lifters/scrc.py:1496

  composer 的真实过程是：

  读取 J
  读取 interface
  读取 C.schedule 的 slot 结构
  读取 C.strategy
  枚举 work items
  根据 strategy 选择 RuleCard
  计算依赖
  稳定拓扑排序
  生成 ReplayPlan π

  见 python/intentir/verify/gate1/composer.py:2022。

  所以更准确的公式是：

  π = Compose(
        J,
        interface,
        C.schedule_slots,
        C.strategy,
        RuleRegistry
      )

  不过有一个重要细节：

  > π 的顺序和 RuleCard 选择是确定性的，但决定源码 realization 的 C.strategy 仍然由 Lift LLM 输出。

  所以 composer 并没有独立理解源码，它只是把 LLM 选择的 strategy 展开为确定性施工计划。

  也就是说现在的结构实际上是：

  LLM 负责选 source strategy
           ↓
  composer 负责把 strategy 展开成 π
           ↓
  Replay LLM 按 π 生成代码

  ## 四、这里存在一个必须面对的三选二

  假设我们坚持：

  1. Intent 只有 J=A+B 和纯调度 C；
  2. Replay writer 看不到源码；
  3. Gate1 要求原始 TTIR 数据流拓扑完全一致。

  这三件事不能同时保证。

  LayerNorm 就是证明：

  Source 1:
    where(mask, centered, 0)
    square
    reduce

  Source 2:
    square
    where(mask, squared, 0)
    reduce

  如果二者具有相同的：

  J = A+B
  C = block/warp/stage

  那么 replay writer 收到的信息完全相同。

  即使它是再强的 LLM，也无法知道原始源码究竟采用 Source 1 还是 Source 2。这不是模型能力问题，而是输入中根本没有这个信息。

  因此只能选择：

  ### 路线 A：保留严格源码拓扑 Gate1

  那么必须额外保存 source realization 信息：

  π
  或者 Wsource -> π

  此时系统就不再只有 J+C。

  ### 路线 B：坚持 Intent 只有 J+C

  那么 Gate1 应比较 canonical semantic structure，而不是 raw SSA presentation。

  例如 LayerNorm 的 Gate1 应比较：

  存在 square
  存在 reduction
  predicate 相同
  inactive contribution = 0
  producer/reduction 语义依赖相同

  而不要求 where 必须位于完全相同的 SSA edge。

  结合你说的 LLM-first 和简洁系统哲学，我认为更适合的是路线 B。

  也就是说：

  > 不应继续给 C.strategy 增加 source topology family，而应重新定义 Gate1 的 hard fingerprint，使它验证语义结构，而不是冻结源码 presentation。

  Gate2 再负责实际数值行为。

  ## 五、masked-J 是谁处理的？

  这里的 “masked-J” 不是 kernel 里的 tail mask，而是一种反泄漏消融。

  它分成四步。

  ### 1. 确定性 Python 代码遮盖 J

  由：

  _masked_rewriter_view()

  完成。python/intentir/verify/gate1/model.py:3985

  例如正常 J：

  {
    "op": "reduce",
    "result": "variance",
    "operands": ["squared"],
    "attrs": {
      "fn": "sum",
      "axes": [1]
    }
  }

  masked-J 后近似变成：

  {
    "op": "<masked>",
    "result": "n3"
  }

  输入输出变成：

  {
    "name": "t0",
    "dtype": "<masked>",
    "shape": ["<masked>", "<masked>"]
  }

  B 中的内容变成：

  {
    "kind": "<masked>",
    "predicate": "<masked>",
    "fill_value": "<masked>",
    "masked_contribution": "<masked>"
  }

  ### 2. 仍然保留 actual π

  masked-J 不会重新根据 masked J compose π。

  它保留 normal Lift 最终生成的：

  实际 ReplayPlan
  实际 rule id
  实际 reference topology
  实际 C.strategy
  实际 RuleCards

  只是把引用改成 n0/a0/p0/c0。

  这正是消融想测试的：

  > 如果 J 的语义被删掉，只靠 π、C.strategy 和 RuleCard，writer 是否仍能重建源码？

  ### 3. Replay LLM 生成一个全新 masked candidate

  ResponsesReplayWriter 收到 masked payload，再调用 LLM 生成代码。python/intentir/verify/gate1/replay.py:342

  所以：

  - “遮盖 J”由确定性代码完成；
  - “根据遮盖后的 packet 生成 replay”仍由 LLM 完成。

  ### 4. Harness 恢复 ABI，再编译比较

  LLM 输出的是：

  scrc_k0(scrc_p0, scrc_p1, scrc_c0...)

  确定性 adapter 把它恢复为源码真实函数名和参数名，然后编译 TTIR、比较 fingerprint。

  如果 masked-J 仍然 hard-close，说明 π/C/RuleCard 泄漏了足够多的语义，normal Lift 作废。

  ## 六、为什么 Lift 时不直接匿名？

  你这个问题是对的：完全可以从 Lift 输出开始就匿名。

  当前只做了一半：

  - node/domain/access/effect 等 Lift-owned ID 已要求 n0/d0/a0/e0；
  - 但 tensor 名、函数名、interface 参数名和 schedule slot 名仍可保留源码 spelling；
  - 到 replay handoff 时再统一匿名；
  - IntentProgram 又重新保留真实名字。

  当前 prompt 明确允许：

  > only trusted interface parameter and schedule-slot names may retain their required ABI spelling

  见 python/intentir/extraction/lifters/scrc.py:545。

  之所以这么做，主要是因为当前 harness：

  - 按参数名调用 Triton；
  - 要求 replay 函数签名与源函数一致；
  - 通过真实参数名关联 CompileCase；
  - 通过真实 constexpr 名注入 C。

  但这些并不是 J 必须保留名字的理由。

  更简单的设计完全可以是：

  源码签名：
    layer_norm(X, Y, N, BLOCK_SIZE)

  进入 Lift 前立即建立：
    X          -> p0 / t0
    Y          -> p1 / t1
    N          -> p2 / x0
    BLOCK_SIZE -> c0

  Lift 输出：
    J 只使用 t0/t1/x0/n0/v0
    C 只使用 c0

  Harness sidecar：
    p0 -> X
    p1 -> Y
    p2 -> N
    c0 -> BLOCK_SIZE

  需要编译源码或 replay 时，由 harness 恢复映射。

  这会带来几个直接好处：

  - J digest 对纯重命名不敏感；
  - J 不会通过 variance、hidden_size 等名字泄漏语义；
  - 不需要每次构造额外 opaque rewriter view；
  - Triton、TileLang、CUDA 的来源参数名不会污染统一 Intent；
  - 多来源更自然。

  需要注意：匿名化的是“名字”，不是语义。

  必须保留：

  参数顺序
  dtype/rank
  输入输出关系
  shape 相等关系
  scalar 是否参与计算
  reduce fn/axes
  predicate/fill

  这些是语义结构，不应 mask。

  ## 七、为什么要 ABI / IntentProgram？

  IntentProgram 是当前分支提交 f994c48 引入的，主线没有。

  它最初想解决的真实问题是：

  > 旧 backend 只消费 IntentFunction，但完整 B 在外层 SemanticArchive.boundary，可能被 lowering 静默丢掉。

  所以开发者增加了：

  IntentProgram {
    function
    boundary
    logical ABI
    optional C
  }

  目的是强制 backend 同时接收 A+B，并对每个 B obligation 返回 consumed/checked/unsupported。

  这个动机是合理的，但解决方案偏重：

  - 新增第二套 canonical wire schema；
  - 新增 typed ABI；
  - 新增 Gate1 adapter；
  - 新增三个 digest；
  - 新增 backend protocol；
  - 新增 obligation ledger；
  - 与原 Gate1 artifact 和旧 IntentFunction.layer_c 并存。

  ### 我对你观点的判断

  你说：

  > IntentProgram 应该只是内部 harness 处理框架，而不是 Intent 本身的一层。

  我赞同。

  我们不需要把它定义成新的对外 IR 真值。真正的 Intent 可以保持：

  Intent {
    J = A + B
    C
  }

  backend 直接：

  lower(Intent, target)

  至于运行时必须知道的：

  源码函数名
  参数真实名字
  实参
  grid
  设备
  case
  opaque -> source name map

  可以放到：

  HarnessContext

  它不是 Intent，不进入 J digest，也不交给 source-blind writer。

  ### “完全不需要 ABI”要稍微修正

  不需要单独的 LogicalABI 语义对象，但运行时总要有一个很薄的 binding：

  p0 是第一个参数
  p1 是第二个参数
  t0 对应 p0
  输出写到 p2

  否则无法调用 kernel。

  不过这可以只是 harness 的数组/映射，而不需要 183 行 ABI schema，更不需要放进 IntentProgram。

  语义上的输入、输出、dtype、shape 应已经存在于 A；destination、alias、inout 应存在于 B。不要再复制一套 ABI 真值。

  ## 八、C 现在到底怎么被消费？

  当前其实有两套完全不同的 C 消费方式。

  ### 1. Gate1 replay 中消费 C

  #### Replay LLM

  Replay writer只看到：

  C slot 名称/类型

  看不到具体值。

  例如：

  {
    "slots": [
      {"name": "c0", "kind": "constexpr", "value_type": "int"}
    ]
  }

  它生成参数化 kernel。

  #### 编译 harness

  随后 harness 将真实 C 值加入 CompileCase.schedule：

  values.update(schedule)
  kernel.warmup(grid=grid, **values)

  见 python/intentir/verify/gate1/_triton_worker.py:259。

  源 kernel 和 replay kernel 使用同一份 C 编译。

  这一部分其实不重，本质只是通用 kwargs 注入。

  ### 2. C.strategy 的消费

  这部分比较重：

  C.strategy
     ↓
  composer 选择 RuleCard
     ↓
  生成 π
     ↓
  Replay LLM 根据 π/RuleCard 写源码

  LayerNorm 的 mask placement 就走这条路径。

  因此现在所谓 C 混了两种性质：

  C.schedule  = 编译参数
  C.strategy  = source replay 施工选择

  这正是应该拆掉的地方。

  ### 3. Gate2 中消费 C

  Gate2 执行 source 和 replay 时，直接把：

  artifact.schedule.values

  作为 Triton launch kwargs。python/intentir/verify/gate2/triton.py:132

  scalar J lowering忽略 C，因为 scalar leg 验证的是 J 语义。

  这很合理。

  ### 4. 新 typed CUDA lowering

  当前新 CUDA lower_program_to_cuda() 虽然接收带 schedule_hint 的 IntentProgram，但实际只使用：

  program.function
  program.boundary
  broadcast contracts
  target
  variant

  没有真正读取 schedule_hint。

  所以新 lowering 中 C 目前只是：

  可替换
  可计算 digest
  但未实际消费

  ### 5. 历史 production lowering

  归档的旧 lowering 会读取：

  num_warps -> block_threads

  然后根据图结构选择 row/elementwise schedule，最后转换成 MLIR pass 参数。

  但这条路径位于：

  verify/back/gate2_production_lowering_v1

  已经明确归档，不是当前 Gate2 主线。

  ## 九、按照你说的哲学，我建议最小化成这样

  Source
    │
    ▼
  Lift LLM
    │
    ▼
  Intent {
    J = A + B
    C = schedule/performance hints
  }
    │
    ├──────────────┐
    ▼              ▼
  Replay LLM       Lower LLM/backend
    │              │
    ▼              ▼
  same frontend    target artifact
    │              │
    ▼              ▼
  Gate1            backend conformance
    │
    ▼
  Gate2 source↔replay
        source↔semantic reference

  旁边只保留一个很薄的、非语义 harness：

  HarnessContext {
    opaque source binding
    concrete inputs
    grid
    C values
    target/device
  }

  ### 可以删除或降级的东西

  如果正式选择“Intent 只有 J+C”：

  - 删除 C.strategy 作为 Intent 字段；
  - 停止为每种源码 topology 添加 StrategyFamily；
  - π 不再作为庞大的确定性施工计划；
  - RuleRegistry 不再为每种源码形态增加专卡；
  - IntentProgram 降为临时 Python wrapper，或者直接删除；
  - LogicalABI 降为 harness binding；
  - J 从 Lift 输出时就使用 canonical opaque handles；
  - Gate1 从 raw SSA topology equality 改为 semantic structural fingerprint equality；
  - Gate2 保持实际执行差分。

  ### 仍然需要保留的确定性部分

  LLM-first 不意味着所有代码都交给 LLM。以下部分必须是确定性的，但可以很小、很通用：

  JSON/schema 基础校验
  source/replay 隔离
  opaque handle 映射
  编译
  指纹提取
  比较
  C 值注入
  Gate2 执行和数值比较

  这些是实验裁判，不是 per-kernel 前后端规则。

  真正应该避免的是：

  为每种 kernel/source topology
  在确定性代码里写一套 realization 施工逻辑

  ## 十、我现在最明确的判断

  1. deterministic composer 确实是主线设计，不是当前分支临时改的。
  2. 但当前分支继续扩大了它：preheader、fusion、mask placement 都是在增加 source-specific patch surface。
  3. IntentProgram/ABI 是当前分支新增，不是原始主线必需结构。
  4. IntentProgram 的动机是防止 backend 丢 B，但可以通过“backend 必须直接消费完整 J=A+B”更简单地解决。
  5. 参数完全可以在 Lift 输出时就匿名；真实名字只需要保留在 harness sidecar。
  6. 如果坚持 Intent 只有 J+C，就必须停止要求 raw TTIR presentation 完全一致。否则 source realization 信息无处可来。
  7. 我建议的最终原则是：

  Intent 真值：J + C
  源码绑定：HarnessContext
  Gate1：canonical semantic structure
  Gate2：actual behavior
  Lower：J 必须消费，C 可选消费/重调

  这比当前 J + interface + schedule + strategy + π + RuleRegistry + IntentProgram + ABI 更符合你最初的 LLM-base、多来源和低工程负担目标。

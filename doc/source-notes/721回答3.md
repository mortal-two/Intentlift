  - 根据 J 枚举 work item；
  - 选择 RuleCard；
  - 从 C.strategy 推导 π；
  - 为 reduction/fusion/pipeline 编写施工算法；
  - 稳定拓扑排序后替 LLM 决定怎么写 kernel。

  ## 1. 关于 async pipeline，我上一轮说重了

  我之前写：

  > 架构分层已经明确，但一般 async pipeline correctness contract 尚未闭合，只支持已审计的受限 pattern。

  这句话隐含了一个不正确的方向：仿佛我们必须预先在 J/B 里建立完整的 async-copy、barrier、token、wait、double-buffer 状态机，才能支持 pipeline kernel。

  这会再次走向重规则系统。

  更正确的分析是：

  ### 普通软件流水线不属于 J

  假设源码是：

  async_copy(tile[k+1])
  compute(tile[k])
  wait(tile[k+1])
  swap_buffers()

  如果它最终计算的逻辑结果只是：

  Y = Matmul(X, W)

  那么：

  J：
    contraction(X,W)

  C：
    pipeline depth
    prefetch distance
    double buffer
    tile size

  π：
    源码用了怎样的 async-copy/wait/buffer-swap 拓扑

  J 不需要保存：

  - cp.async；
  - wait_group；
  - barrier 放在哪一行；
  - ping-pong buffer 编号；
  - source stage count；
  - shared-memory 地址。

  这些都不是 kernel 的数学语义。

  Replay LLM 根据 π 重建相同 pipeline；Gate1 比较 TTIR，检查源码 realization 是否闭合。目标 lowering 可以完全不用同一 pipeline，例如 RVV 上改为普通 load/
  vector loop。

  ### 什么时候 pipeline 内容才进入 J

  只有当某种顺序本身属于可观察语义，例如：

  - 跨线程通信改变逻辑结果；
  - 有状态 recurrence；
  - 一个迭代必须看到前一迭代产生的逻辑状态；
  - 读取旧值还是新值会改变输出；
  - race/atomic 顺序被程序显式观察。

  此时进入 J 的仍然是：

  逻辑依赖
  状态转移
  允许的观察顺序

  不是 barrier/cp.async 这些具体实现。

  因此针对 reviewer 的正确回答应是：

  > IntentIR 可以接受带 software pipeline 的源码。流水线本身作为 source realization 由 π 保留，stage/prefetch 等可调选择进入 C；J 只保留流水线最终实现的逻
  > 辑计算和真正可观察的状态依赖。是否支持某个具体 pipeline，不靠预先注册 pattern，而由 LLM replay 能否通过严格 Gate1 决定。

  也就是说，不再说“只支持已审计 pattern”，而应说：

  > 支持范围由 Gate1/Gate2 动态认证；没有闭合的样本就是 unsupported，不需要先给每种 pipeline 写规则。

  ## 2. 在线检测最多只能选择一项

  这个约束非常重要，我上一轮列出的：

  masked-J
  J mutation
  π swap
  C swap
  π dropout

  不能全部放进正式系统。

  每一项都可能意味着：

  - 再调用一次 Replay LLM；
  - 再生成 kernel；
  - 再编译；
  - 再提取 TTIR；
  - 甚至再遍历多个 C profile。

  这会让本来已经昂贵的重放成本成倍增加。

  ### 正式在线 Gate1 应当是

  1. Lift LLM 一次
     -> J + C + π

  2. Replay LLM 一次
     -> normal replay

  3. 编译 source/replay
     -> exact Gate1

  4. 只有 normal Gate1 闭合后：
     再做一次 masked-J replay

  5. Gate2

  不应该：

  - 对每次 relift 都做 masked-J；
  - 在线跑多个 semantic mutation；
  - 在线做 π swap；
  - 在线做 π dropout；
  - 在线遍历完整 fixed-C family；
  - 在线运行 RuleCard neutralization。

  这些全部放到论文的离线消融实验中。

  ### 在线唯一选择哪一个？

  我建议仍然选择 masked-J。

  因为我们最关心的问题就是：

  > writer 删除 J 后，只靠 π+C+所有其他非源码通道，是否还能重建源 kernel？

  它一次性攻击所有辅助通道，比“只修改一个 add→mul”覆盖面更广。

  但 masked-J 必须运行在简化后的架构上：

  保留：
    π 的匿名 realization topology
    C
    匿名参数结构
    全局 frontend prompt

  删除：
    J 的语义

  不存在：
    selected RuleCard
    C.strategy
    realize_reduce 之类 semantic rule id
    按当前 kernel 选择的 API mapping

  当前 masked-J 保留 realize_reduce 和 tl.sum，所以当前实验设计需要随 composer/RuleCard 一起重构。

  ### 其他消融放哪里

  论文离线 evaluation 可以做：

  - J-only：删除 π；
  - masked-J：删除 J；
  - π swap；
  - J semantic mutation；
  - C swap；
  - 老 composer/RuleCard 与 LLM-only 对比；
  - 多模型、多 seed、不同 kernel family。

  这些用于证明论文机制，但不进入每个 kernel 的正式认证路径。

  ## 3. J 不应随着 reviewer 问题继续膨胀

  上一轮我又接近了这种错误方向：

  遇到 atomic
    -> 增加完整 AtomicContract

  遇到 pipeline
    -> 增加 AsyncPipelineContract

  遇到 fusion
    -> 增加 FusionContract

  遇到 copy
    -> 增加 CopyOp

  这和为 π 添加 RuleCard 本质相同：不断把系统变成手写分类器。

  更好的 J 不是“列举所有 kernel 种类”，而是一套很小的、可组合的语义语言。

  ## 4. 我建议把 J 收敛为五类语义构造

  J = A + B

  ### A：逻辑值和状态关系

  A 只需要五种核心能力。

  #### 1. Elementwise expression

  不是为 exp/add/mul/sigmoid 分别设计施工规则，而是：

  map(inputs, scalar-expression)

  例如：

  map(x,y, expr = x * sigmoid(y))

  scalar expression 可以是一个小型表达式 AST。

  #### 2. Logical index/map

  统一表达：

  - copy；
  - reverse；
  - transpose；
  - reshape；
  - slice；
  - gather；
  - broadcast。

  核心是：

  output[index] = input[index_map(index)]

  因此：

  copy:    Y[i] = X[i]
  reverse: Y[i] = X[N-1-i]

  自然在 J 中不同，不需要 CopyRule 和 ReverseRule。

  #### 3. Aggregate

  统一表达：

  - reduce；
  - scan；
  - contraction；
  - segment reduction。

  例如：

  reduce(input, axes, combiner, identity)
  contract(A,B,index-relation)

  #### 4. Semantic recurrence

  只在算法本身有状态递推时使用：

  - FlashAttention online softmax；
  - recurrence；
  - 数据依赖循环；
  - scan state；
  - iterative update。

  普通 K-tile loop、pipeline loop、unroll loop不进入这里。

  #### 5. Logical update

  统一表达：

  - scatter；
  - histogram；
  - in-place update；
  - duplicate-index accumulation；
  - atomic 实现的逻辑更新。

  例如：

  update(
    base=t0,
    key=index(i),
    value=update_value(i),
    combine=add
  )

  J 描述“多个 update 如何形成最终逻辑值”，不描述它使用 atomicAdd、sort-reduce 还是分块私有化。

  ### B：最小的正确性边界

  B 不应变成所有硬件并发机制的百科全书，只保存会改变可观察结果的内容：

  domain / bounds
  predicate / fill
  logical destination
  alias / in-place
  partial write coverage
  duplicate/conflict policy
  允许的数值顺序或 tolerance
  observable state dependency

  不进入 B：

  warp
  barrier spelling
  cp.async token
  shared-memory bank
  pipeline stage
  double buffer
  pointer association
  source fusion placement

  这能同时覆盖 reviewer 的问题，又不会为每种实现写 contract。

  ## 5. fusion、atomic、copy、pipeline 在新结构中的位置

   情况                  J                                      C                         π
  ━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   copy                  identity logical map                   tile/vector               源码 load/store 拓扑
  ────────────────────  ─────────────────────────────────────  ────────────────────────  ──────────────────────────────
   reverse               reverse index map                      tile/vector               源码地址构造拓扑
  ────────────────────  ─────────────────────────────────────  ────────────────────────  ──────────────────────────────
   elementwise fusion    组合 value DAG                         target fusion/grouping    源码 fused producer/reuse
  ────────────────────  ─────────────────────────────────────  ────────────────────────  ──────────────────────────────
   reduction fusion      value DAG + aggregate                  target fusion/tile        源码共享 load/loop placement
  ────────────────────  ─────────────────────────────────────  ────────────────────────  ──────────────────────────────
   atomic add            logical update + conflict/order要求    privatization/tile        源码 atomic realization
  ────────────────────  ─────────────────────────────────────  ────────────────────────  ──────────────────────────────
   async pipeline        最终逻辑计算                           stage/prefetch/buffer     async-copy/wait/swap 拓扑

  关键点是：

  > fusion、pipeline、atomic 指令不是新增 J op family；J 保存它们实现的逻辑关系。

  ### Atomic 什么时候需要“允许结果集合”

  只在并发顺序会真正改变可观察结果时。

  例如浮点 atomic add 的不同线性化顺序可能产生不同舍入结果，那么 B 可以简单写：

  conflict = accumulate
  order = unspecified
  numeric = tolerance(...)

  这表示多个合法结果。

  但如果是整数 histogram：

  count[bucket] += 1

  加法精确且顺序不影响结果，J 仍然是普通单值函数，不需要为了源码用了 atomic 而把整个 J 定义成复杂关系。

  因此也不需要一开始就为所有 kernel 引入庞大的 nondeterministic semantic framework。

  ## 6. π 应该是什么：LLM 直接生成的匿名 realization graph

  目标 π 不应是：

  RuleCard 列表
  composer work items
  C.strategy 展开结果

  它应当只是一个很薄的匿名 realization graph，例如：

  {
    "instances": [
      {"id": "r0", "semantic_ref": "a0", "region": "q0"},
      {"id": "r1", "semantic_ref": "n2", "region": "q0"},
      {"id": "r2", "semantic_ref": "n3", "region": "q0"}
    ],
    "routes": [
      {"from": "r0", "to": "r1", "operand_slots": [0, 1]},
      {"from": "r1", "to": "r2", "operand_slots": [0]}
    ],
    "order": [
      ["r0", "r1"],
      ["r1", "r2"]
    ],
    "sharing": [
      {"value": "r0", "consumers": ["r1:0", "r1:1"]}
    ]
  }

  LayerNorm 中：

  - a0 是什么 predicate/fill，只在 J 中；
  - n2 是 mul，只在 J 中；
  - π 只说 a0 的一个 realization 被复用到 n2 的两个输入；
  - Replay LLM 自己根据 J+π 写 Triton；
  - 没有 reduction_mask_placement；
  - 没有 realize_reduce；
  - 没有 RuleCard；
  - 没有 composer。

  对于 pipeline，π 还可以有 realization-only region/placement 描述，但仍由 Lift LLM直接生成，不需要预注册 pipeline family。

  确定性代码只检查：

  r0/r1/r2 是否唯一
  semantic_ref 是否存在
  route 指向是否合法

  不重新排序，不推导步骤，不展开规则。

  ———

  ## 7. Gate1 如何证明 J 是语义

  我们的证明不需要宣称 π 与语义完全统计独立，因为源码拓扑天然与语义相关。

  需要证明的是：

  ### 语法上

  [
  \llbracket \pi \rrbracket
  ]

  单独没有 kernel denotation。

  π 只能引用：

  J node
  J access
  J value
  realization region
  edge/slot/order/share

  π 不能声明：

  操作符
  常量
  predicate
  fill
  reduction fn
  logical index map
  output mapping
  conflict combiner

  因此所有语义原子只能由 J 提供。

  ### 构造上

  正常 Gate1：

  [
  F(P)=F(W(J,C,\pi))
  ]

  说明 J+C+π 足以重建 P。

  唯一在线 masked-J：

  [
  F(P)\ne F(W(\operatorname{mask}(J),C,\pi))
  ]

  说明非 J 通道不足以重建 P。

  于是，在 source isolation 和 π 语法无语义原子的前提下，可以把语义归因到 J。

  这里的 masked-J 是对形式定义的攻击测试，不是唯一数学前提。

  ———

  ## 8. 最终收敛版

  Intent：
    J = 小型可组合语义语言 A+B
    C = 纯调度

  Gate1 witness：
    π = Lift LLM 直接生成的匿名 realization graph

  不存在：
    composer
    RuleCard
    C.strategy
    LogicalABI 语义对象
    重型 IntentProgram wire format
    per-kernel deterministic policy

  在线：
    normal replay Gate1
    + 最多一次 masked-J
    + Gate2

  离线论文消融：
    J mutation
    π swap
    J-only
    π dropout
    C swap
    multi-model/multi-seed

  所以，这次真正的重新思考结果是：

  > 我们不需要预先“支持 fusion/atomic/pipeline 的所有实现 pattern”。J 只需要一个小型、通用、可组合的语义核心；Lift LLM 负责把任意来源归纳到这个核心，π 负
  > 责保留源码 realization，Replay LLM 负责重建。是否成功由 Gate1/Gate2 裁决，而不是由 composer/RuleCard 的覆盖表决定。

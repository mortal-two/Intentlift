# IntentOp 健壮性审计：真实机制、已证能力与下一语义核心

> 状态：2026-07-21 Task02 的 source-grounded 审计结论  
> 原则：能力名必须对应真实 consumer；JSON 能保存一个名字不等于系统支持它。

> 2026-07-22 后续状态：Typed Relations 03 已实现本审计第 7 节要求的首版
> `IndexBoundsSpec`、`LogicalUpdateSpec`、`ResultRelationSpec` 和 J-owned Gate2 comparator。
> CPU scatter executor 仍按真实能力 fail closed；下文“尚未类型化”是 Task02 当时的历史
> 边界，不是当前 schema 状态。

## 1. 结论先行

当前仓库还不能诚实地宣称“一个已经冻结的 IntentOp 核心覆盖 copy、reverse、fusion、
recurrence、atomic/update 与 async pipeline”。本次审计完成的是更重要的前置工作：

1. 删除了 `IntentOp.layer_b` 这一第二 B 通道；
2. 删除了 destination `out` 这一逐 op writeback 旁路；
3. 删除了 canonical J 中的 `trip.tile_hint`，loop tile 只能由 C 显式传给 lowering；
4. 从 J 的 access/effect kind 中删除 `atomic` 与 `synchronize`，改为抽象的 logical
   `update`；具体 atomic、async 与 barrier 仍只存在于 π；
5. 为 Gate2 scalar 建立实际 lowering 能力边界，未被
   `ConvertIntentToLinalg` 完整消去的 op 在调用外部编译器前 fail closed；
6. scatter/update 在 duplicate、conflict、order、result relation 未类型化前，正式 E_J 与
   direct CUDA 一律 fail closed；
7. 用固定 digest 的真实源码纠正了两个错误样本标签。

因此，这一阶段是“回收错误 claim 并建立可审计边界”，不是再增加一批看似覆盖、实际没有
统一 denotation 的 named op。

## 2. 三个删除项为什么必须一起删除

### 2.1 `op.layer_b`

过去同一语义事实可能同时出现在：

```text
op.attrs
op.layer_b
J.boundary
```

emitter 还会读取 `op.layer_b` 生成 `intent.index_bounds_proven`、in-place ABI attribute 或
accumulator dtype，而 E_J 不完整消费这张任意字典。这意味着同一 Layer-A 图可以因一个
没有形式 denotation 的旁路字段产生不同代码。现在 direct model、Lift schema 与 Gate1
strict parser 都拒绝它。

### 2.2 `op.out`

`out` 把逻辑 value binding、外部 destination 和 alias/writeback 混成一个字段。现在：

- 纯 Layer-A 输出使用同名 result，或函数级 `returns[{output,value}]`；
- alias、partial write 与 observable destination 只能进入 canonical J boundary；
- bare `IntentFunction` emitter 不再从逐 op 注释猜 `intent.inplace`。

### 2.3 `trip.tile_hint`

semantic loop 的 trip 只说明逻辑迭代轴。lowering 若需要 chunk size，必须通过显式
`schedule_tile` 接收 C 的投影；无 C 时使用完整逻辑轴这一保守实现。lowered
`intent.loop` MLIR 中仍可出现 `tile_hint` attribute，因为那已经是 C 被消费后的低层
调度 IR，不是 canonical J 字段。

## 4. 实测 capability matrix

符号：`✓` 为当前路径有可执行测试；`△` 为能表示或有历史/专项 lowering，但没有当前完整
Gate 闭环；`×` 为当前正式路径 fail closed。

| 构造 | strict J parse | 历史 NumPy witness | Gate2 scalar E_J | direct CUDA J | 结论 |
|---|---:|---:|---:|---:|---|
| copy（function `returns`） | ✓ | ✓ | ✓ | △ | 最小值语义已闭合；尚需真实 Source/Replay batch |
| elementwise→reduce fusion DAG | ✓ | ✓ | ✓ | △ | fusion 不需要独立 semantic op；J 必须保留完整 producer DAG |
| transpose | ✓ | ✓ | `ConvertIntentToLinalg` 有 pattern | △ | 还没有本任务的真实 Gate1 claim |
| reverse / `flip` | ✓ | ✓ | × | △（旧专项 pass） | 当前官方 E_J 不支持，不能声称 Gate2 闭合 |
| dynamic gather（in-bounds challenge） | ✓ | ✓ | ✓ | △ | data-dependent read 可执行；通用 bounds/OOB B 尚未类型化 |
| `scan` | ✓ | ✓ | × | △（旧专项 pass） | op 名存在不等于当前 E_J 支持 |
| structured semantic loop | ✓ | ✓（历史 witness） | × | ×（flat direct path） | recurrence 的正式 Gate2 尚未闭合 |
| scatter / duplicate update | ✓ | ✓（单一顺序 witness） | × | × | 缺 duplicate/conflict/order/result relation，必须 unsupported |
| async pipeline | 不应成为 J op | 不适用 | copy J 可执行 | frontend observer 待接入 | async/barrier/stage 只属于 π/C |

Gate2 scalar 当前明确支持的 flat op 集是：

```text
cast, concat, const, contraction, gather, iota,
map_binary, map_unary, pad, reduce, select, transpose
```

这个集合是 executor conformance boundary，不参与 Lift/Replay 生成，也不是 RuleCard。

## 5. LayerNorm 拓扑争议的最终解释

真实源码明确写成：

```text
xbar = where(cols < N, x - mean, 0)
var  = reduce(xbar * xbar)
```

如果 J 只写一个数学摘要，而 Replay 产生：

```text
square = centered * centered
var = reduce(where(mask, square, 0))
```

两者可能在特定输入上数值相同，但 strict TTIR observer 看到的数据流不同。因此：

- J 的 value DAG 必须保留 `select -> mul -> reduce`；
- π 引用这些已有节点，描述 source 选择的 placement/share/order；
- π 不能重新声明 mask、zero 或乘法；
- Gate1 对 normalized TTIR 拓扑要求一致；
- Gate2 再检查 source↔replay 与 source↔E_J 数值关系。

π 的作用正是让 LLM 能重建这一 source realization，而不是让确定性 composer 猜规则。

## 6. update 与 allowed-result relation：当前为什么必须停在 unsupported

`scatter(reduce=add)` 只说明一个 combiner 名，仍没有回答：

```text
indices 是否保证唯一？
重复时按输入顺序、任意顺序还是数学多重集组合？
overwrite 冲突允许哪一个 writer？
浮点重结合允许多大误差？
结果是单值、tolerance relation，还是 one-of-updates 集合？
```

把 `tl.atomic_add` 写进 J 并不能回答这些问题；它只是某个 target realization。把 NumPy
`add.at` 的一个顺序结果当唯一 golden 同样错误。因此本次没有仓促增加 `AtomicOp`、
`HistogramOp` 或自由格式 `conflict_contract`。正式路径在 typed relation 落地前拒绝
scatter/update。

下一步应只增加一个通用 logical-update relation，并至少类型化：

```text
destination/key/value
combiner
duplicate policy
observable order
result relation: exact | tolerance | one-of-updates（或更严格关系）
```

Gate2 对单值语义做 equality/tolerance；对 relation-valued 语义检查 source 与 replay 各自
是否属于同一个 `R_J(x)`，而不是强迫二者等于某次任意执行。

## 7. 下一步 schema 工作，按依赖顺序进行

1. 定义 typed logical map/access：domain dim、runtime scalar、SSA value index、predicate、
   fill/OOB；用 copy/reverse/dynamic gather 三个正交样本闭合。
2. 定义 logical update 与 result relation；用 xFormers unique update、Liger duplicate
   embedding add 和一个真实 racing-overwrite 样本区分三种 contract。
3. 让 Gate2 comparator 从同一个 J 读取 relation；删除“仅由 case harness 决定 tolerance”
   的语义旁路。
4. 让 scalar E_J 支持 ordered recurrence，或继续明确 unsupported；不得拿历史 NumPy
   interpreter 冒充当前 Gate2 第三条边。
5. 上述构造冻结后，再开始 28 个真实 Kernel 的 LLM Lift/Replay/Gate1/Gate2/perf 批次。

这里不需要 RuleCard、composer 或 kernel recognizer。LLM 负责产生组合 J 与 π；固定代码
只做 closed schema、consumer capability、执行与裁决。

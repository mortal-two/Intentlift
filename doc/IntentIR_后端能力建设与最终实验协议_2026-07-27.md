# IntentIR 后端能力建设与最终实验协议

> 日期：2026-07-27  
> 状态：后端能力与论文实验的新执行基准  
> 适用范围：当前 28 个 high-performance direct-symbol registry；正式实验只纳入已完成 exact
> evidence intake 的 fresh accepted J
> 上位语义边界：accepted `J=A+B`、可擦除 `C`、统一 Q/D execution-domain closure

本文首先约束**后端应当具备什么能力**，其次才定义如何用实验展示这些能力。不能为了迁就当前
artifact、已有候选或已经跑出的数字而缩小后端；也不能为了扩大性能实验，静默修改 accepted J 后仍
沿用原证书。后端开发允许构造手工 shape/dtype 变体，但必须与 SCRC-certified artifact 分账。

## 1. 第一性原理目标

生产后端接收同一个 typed computation reference `J`，在 target 上形成、验证和搜索不同的真实 MLIR
states。它需要提供两种相互独立的自由度：

1. **Schedule freedom**：固定结构路径，重新选择 tile、vector、threads、pipeline、memory placement；
2. **Lowering freedom**：从同一 J 形成不同 fusion、materialization、reduction、scan、contraction、
   stage decomposition 等 MLIR 路径，并分别调 schedule。

`C` 只保存可能有用的 Source implementation prior；它既不是 target commitment，也不扩大合法状态
空间。后端能力的验收单位不是某个 benchmark 是否加速，而是：

```text
(typed workload,
 target,
 concrete MLIR state,
 correctness receipt,
 performance receipt)
```

某条 transformation 对一个 kernel 不适用时，必须留下 `not_matched` 或 hard rejection；不能因此从
28 项横向矩阵中删除该 kernel。

## 2. 对象所有权：dtype、shape、C 与 Harness

必须区分四类事实：

| 事实 | 所有者 | 后端能否改变 |
|---|---|---|
| 输入/输出 tensor dtype、显式 cast、reference op dtype | J/A | accepted J 内不能静默改变 |
| literal shape、symbolic axes、layout、observable ABI | J/A+B | 只能绑定 J 已声明的 symbol |
| concrete input values、symbol valuation、runtime stride/grid binding | Harness | 必须满足 J 与 invocation contract |
| tile、threads、vector width、pipeline、候选顺序 | C / backend search state | 可 retile、忽略或重新搜索 |
| FMA、TF32、approximation、内部 accumulator precision | backend lowering state | 保持 hard boundary 后由 Q/D 裁决 |

因此：

- boundary `fp16/bf16/fp32` 不属于 C；擦除 C 后 ABI 与 `M0` 必须不变；
- Harness 可以创建符合 J dtype 的 tensor，但不能把 `tensor<...xf32>` 自行换成 BF16；
- TF32 是 FP32 contraction 的内部执行方式，不是 Harness 输入 dtype；
- backend 可以尝试 observation-changing internal precision state，但输出 carrier/ABI 仍保持 J，并在
  冻结 Q/D 上过滤。

未来若 J 显式声明 type variable，例如 `T in {f16,bf16,f32}`，Harness 可以绑定 `T`；这仍然是 J
valuation，而不是 Harness 自己选择新语义。当前 artifact 的 dtype 都是 concrete specialization。

## 4. 后端开发允许的手工 J 变体

当前 workload profile 只能绑定 J 已声明的 symbolic axes，不能改变 literal shape 或 dtype。为了不让
旧 concrete artifact 限制后端能力，允许构造手工 **development J variant**，记作 `J_dev`。

`J_dev` 可以用于：

- 实现新的 dtype lowering；
- 扩展 shape、tail、layout、stride 与 grid 能力；
- 开发 schedule/lowering search；
- 运行 Target--RefDev、Target--Source correctness 与性能工程；
- 在 28 项横向 capability matrix 中留下真实 compile/execution evidence。

但必须满足以下协议：

```text
intentir.backend.dev-j-variant.v1
base_j_digest
variant_j_digest
source_kernel_id
shape_config_id
dtype_config_id
edits[] = {json_path, old_value, new_value, upstream_evidence}
certification_status = uncertified_backend_dev
allowed_claims = [backend_capability, target_correctness_on_recorded_QD, performance]
forbidden_claims = [scrc_certified, inherits_gate1, inherits_gate2]
```

硬规则：

1. 不原地覆盖 accepted snapshot；
2. 修改 shape/dtype 后生成新的 `variant_j_digest`；
3. signature、A op types、显式 cast、B carrier、shape relation、access、output、Harness、RefEval 与 C
   valuation必须一致修改，不能只改 tensor 字符串；
4. receipt 必须写 `j_unchanged=false`，不能复用 symbolic-valuation 的 `j_unchanged=true`；
5. `J_dev` 不进入 SCRC closure 统计；
6. 当某个 dev variant 要进入端到端论文主张时，再由前端产生 fresh accepted J 并执行
   Lift/TypeCheck/Replay/Gate1/Gate2；旧证书不作废，二者并存。

这不是为实验伪造证书，而是让后端以正确 shape/dtype 先完成通用 compiler capability。Task15 已实现
该 protocol：variant 额外绑定 `base_snapshot_digest/base_c_digest/variant_snapshot_digest/receipt_digest`，
canonical elaborator重建派生类型，consumer 对 authoritative base 重放 exact edits；配套 dev-workload
配置 digest-pin 真实 Source adapter。它仍进入普通 `materialize_j -> MLIR -> target`，没有另造 kernel
emitter。首批 RMSNorm/DYT 自然 FP32 slices 已跑通，BF16/FP16 仍是下一阶段 capability gap。

## 6. Shape 选择：三层而不是 Small/Medium/Large

每个 kernel 的 shape 分成三层：

1. **capture seed**：当前 SCRC c0，小 shape，只验证旧证书与 intake；
2. **capability config**：可由 `J_dev` 手工构造，用于补齐真实 shape/dtype/tail/layout/target能力；
3. **paper config**：来自上游 benchmark或真实模型调用；若要声称完整 SCRC→backend 链，必须有对应
   accepted J，否则明确标记为 backend-dev evidence。

禁止统一命名为 small/medium/large。图表直接写模型或参数：

```text
Llama-3-8B: BT=4096, H=4096
Qwen2.5-7B mRoPE: T=2048, Hq=28, Hkv=4, D=128
FlashAttention: B=4, H=16, S=8192, D=128
xFormers decode SplitK: B=1, Mq=1, H=16, KV=4096, D=256, split=4
```

## 8. 后端能力矩阵与验收

对每个 `(kernel, config, dtype, target)`，后端至少要记录：

```text
base/variant J digest
shape/dtype config provenance
deterministic Intent MLIR digest
ContractView consumed/missing facts
matched/admitted/rejected lowering transitions
post-pass MLIR/topology digest
target binary/object digest
Target--Ref correctness
Source/Replay direct edges（存在时）
schedule candidates and winner
latency and search cost
```

CUDA 与 RVV 都必须由真实 MLIR/C++/upstream compiler lowering 生成 target code；Python 只编排、绑定、
比较和计时。28 项均进入 coverage matrix，即使某条新 transformation 只匹配其中一部分。

能力路线按结构横向补齐：

1. elementwise、tail-safe vector、grid traversal：#1/#6/#10/#17；
2. normalization/loss：#2/#3/#5/#7/#8/#9/#12/#13/#14/#16/#23/#24/#25；
3. indexed/in-place RoPE：#4/#11/#15；
4. contraction/Flash：#18--#23；
5. SplitK partial/reduce/backward：#26--#28；
6. CUDA 与 RVV 共享高层 A/B matcher，target-specific 部分只在 terminal lowering/schedule。

## 9. 最终性能实验只保留四个问题

### 9.1 外部竞争力

GPU：

```text
Source / Best Applicable / IntentIR
```

RVV：

```text
Triton-CPU / Best Native RVV / IntentIR
```

所有 baseline 必须严格匹配 op、shape、dtype、layout、output relation 与计时边界。Source 已是 strongest
applicable implementation 时合并为 `Source / Best`，不重复画柱。

### 9.2 内部归因

GPU 与 RVV 统一三臂：

```text
C-Fixed:
  canonical lowering path
  + target 对 C 的确定性投影 schedule
  + exactly one candidate, no search

Schedule-Only:
  same canonical lowering path
  + target schedule search

IntentIR:
  immutable J
  + multiple admitted lowering paths
  + schedule search within each path
```

主指标：

```text
G_schedule = Perf(Schedule-Only) / Perf(C-Fixed)
G_lowering = Perf(IntentIR) / Perf(Schedule-Only)
```

机器协议 v3 已把 `CF`、`E2`、`E3` 分别冻结为 C-Fixed、Schedule-Only、IntentIR；`E4` 只用于
独立 Erase-C 搜索效率表，`E0/E1/L/N/G` 只保留为 baseline 或补充机制诊断，不进入内部归因主柱。
三臂共享 exact workload、compiler、target、profiler 与 Q/D。对微秒级 CUDA kernel，主要
`G_lowering` 从同一 IntentIR 测量回执中的 schedule spine best 与 expanded best 计算，独立进程的
Schedule-Only/IntentIR 比值仅作漂移诊断。

fusion、materialization、reduction tree、FMA、approximation、local-B 不再作为主图独立柱；它们是
IntentIR 内部真实 transformation。正文最多选 2--3 个 winner 做机制解释。

### 9.3 C prior 小表

固定同一 J、lowering/schedule universe、总候选预算与已测 latency map，只切换 C-guided/Erase-C order。
正文只报：

- 固定预算下 best performance；
- 达到最终最好性能 95% 所需候选数。

C 在某 target 上没有帮助也是合法结果；不能为了得到正数而改变预算或候选集合。

### 9.4 主图 corpus

- 首批正式主图 corpus 以 fresh Task14 的 14 个 high-performance J 为唯一分母；两个 canary、旧
  `production-jc-v1` 中不属于 fresh 14 的历史项以及 `J_dev` 均不得混入该 aggregate；
- 后续 fresh closure 只有在 exact artifact/receipt 到位并完成 content-addressed intake 后逐项扩展，
  不因 Task14 的任务状态自动变成 28/28；
- `J_dev` 可先支持后端能力与性能工程，但若主张完整 SCRC→backend chain，需标明其尚未 certified，
  或换用后续 fresh accepted J；
- component kernels（Flash backward、SplitK）保持 direct-symbol身份，同时在附录报告 composed graph，
  避免把 component 与完整操作的结果混称端到端速度。

## 10. 计时与报告最小协议

主性能表只使用一种预冻结 kernel/graph estimand：

1. candidate 预编译，输入/输出/workspace 预分配；
2. correctness 先于 timing；
3. 少量 untimed code/module/page/device-state warm-up，warm-up 不是结果组；
4. Source、Best、C-Fixed、Schedule-Only、IntentIR 使用相同 cache policy 与计时器；
5. GPU 使用 CUDA event，RVV 使用 pinned core/threads 下 monotonic clock；

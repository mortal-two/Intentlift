# SCRC 多分面 π：计划外候选报告

> 状态：**仅报告，未实现，等待审查**  
> 日期：2026-07-15  
> 报告形成时协议：`normal_no_closure_pi_strict_controlled_causal_v5`；当前实现已升级为
> `normal_no_closure_pi_strict_opaque_refs_causal_v6`，本报告仍仅为未批准候选。  
> 约束：本候选不得在用户批准前进入 artifact schema、Lift prompt、Gate1 verdict、
> held-out batch 或正式实验口径。

## 1. 为什么形成这份候选报告

strict π 恢复为完整、有序施工计划后，五核真实 Lift 的 π 长度为：

| Kernel | π steps |
|---|---:|
| add | 13 |
| row-sum | 12 |
| softmax | 18 |
| RMSNorm | 24 |
| matmul | 18 |

复杂 Kernel 将继续增加 domain、address、mask、compute、effect 和 control 步骤，
因此存在 LLM 注意力被不同职责步骤交叉占用的风险。用户提出把 π 按不同方面并行
处理，本报告只评估该方向，不把它直接加入主线。

当前证据尚不能证明 flat strict π 已达到必须拆分的程度：五核 v5 的 normal replay、
多坐标 paired intervention 和 Gate2 均通过，RMSNorm 的一次 Lift repair 也是非法 ref，
不是 π 长度导致的遗漏。因此现在实施分面 schema 缺少必要性证据。

## 2. 规则卡与 π 仍必须分离

原方案要求：

- π 选择并实例化施工机制；
- 规则卡保存该机制的前端 API 与实现约束；
- writer 只获得 π 选中的规则卡。

这种分离应继续保留。规则卡相当于受控指令集，π 相当于当前 Kernel 的完整调用
计划。把规则卡正文复制进 π 会增加 API/语义泄漏和重复 token；让规则卡自动补全
π 未写的步骤又会恢复隐藏 baseline。当前 strict-v5 的“外部规则定义 + π 显式
选择每一步”是正式主线。

## 3. 候选形式

若后续真实复杂 Kernel 证明 flat π 导致稳定失败，可以把同一 π 表示为互斥分面：

```text
π_full = Compose(
    π_bind_control,
    π_memory,
    π_compute,
    π_effect,
    dependency_contract
)
```

建议职责：

| 分面 | 唯一职责 |
|---|---|
| `π_bind_control` | program domain、runtime scalar、C slot、控制骨架 |
| `π_memory` | address association、mask materialization、load |
| `π_compute` | elementwise、reduce、contraction、cast、select、loop |
| `π_effect` | store、output mapping、atomic/可观察 effect |

这里不能存在四份彼此独立的“真 π”。正式对象仍必须是一个可物化、可审计的
`π_full`，并满足：

- 每个 step 只能属于一个分面；
- 合并结果唯一确定；
- 跨分面依赖显式或可由 J/B 确定性导出；
- 冲突 fail-closed，不允许后一分面覆盖前一分面；
- writer 最终执行完整 `π_full`；
- Gate1、cache identity 和报告保存物化后的完整计划。

## 4. “并行”的允许范围

候选只考虑以下并行方式：

1. source-visible Lift 对各分面独立生成候选；
2. 各分面的 schema、target、coverage 和泄漏检查并行；
3. 确定性 composer 合成一个 `π_full`；
4. 最终仍由一个 source-blind writer 生成完整 Kernel。

暂不建议多个 writer 并行生成 Triton 代码片段。raw code 合并会引入变量命名、
重复 load、mask staging、helper、作用域和施工顺序冲突，并产生一个新的非 SCRC
正确性来源。

## 5. 新增泄漏风险

多分面可能出现“信息秘密分享”：每个 shard 单独看都不泄漏，组合后却恢复 J。
若批准试验，必须同时具备：

- 全部分面使用同一 opaque identifier 映射；
- per-shard 与 combined π 双重静态扫描；
- 跨分面重复语义事实检查；
- 所有分面冻结下的多坐标 J/B paired intervention；
- 单分面 dropout；
- 同类型 Kernel 的分面 swap；
- `Union(shards) == π_full` 的纯代码证明；
- combined masked-J 仍报告，不能只报告单 shard 结果。

## 6. 获得实施批准前必须满足的证据

至少应先出现以下证据之一：

1. 真实复杂 Kernel 的 flat π 在一两次 repair 内稳定漏步骤，而失败与 J/规则卡
   缺失、provider 故障或错误 intervention 合同无关；
2. flat 与 grouped-view 的同模型对照证明 grouped 方式提高正常硬闭合或降低
   replay repair，同时不降低 paired causal coverage；
3. 有纯代码 deterministic composer，且不会从 J/B 自动合成 Lift 漏掉的步骤；
4. 分面方案能保留原方案中的“π 第 N 步”、drop-step、swap 与定位能力。

## 7. 当前决定

截至 2026-07-15：

- 不修改当前 flat strict π schema；
- 不在 Lift/replay prompt 中加入 shard；
- 不改变 Gate1/Gate2 verdict；
- 不建立多 writer 流程；
- 继续用真实复杂 Kernel 检验 flat π 的能力上限；
- 等待用户审查后再决定是否做 test-only grouped-view probe。

因此，本报告满足“计划外特性先报告、后审批”的要求，但不构成实现授权。

## 0. 资源约束下的最终实验边界（优先执行）

后文保留完整设计空间，便于查阅口径；**正式论文与接下来的执行只回答下面一个主张**：

> **IntentIR 将前端碎片化局部化为 Source→J 的前端接入成本，并将新语义局部化为按 J feature 支付一次的 consumer 成本；工程量不再按 frontend × backend × Kernel 的笛卡尔积增长。**

### 0.1 只保留三个可证伪子命题

1. **前端局部性**：从 Triton-centered baseline 增加 TileLang/CUDA 时，主要修改位于 source projection、Lift public context、native compile/run/observer 与 Harness adapter；既有 backend 不按 frontend 增加分支。
2. **分层对应与差异归因**：配对的 TileLang 与 CUDA 独立 Lift 后，不要求得到相等的 J；测量 Layer A 的结构/语义对应程度，并解释 Layer B、ABI、numeric/result authorization 中由真实 Source 差异引起的变化。两边各自走正确证据链——TileLang 以 TIR 结构为硬证据，PTX 只作 ABI-envelope 下的诊断，CUDA 使用放松的 PTX/ABI/effect 证据。
3. **consumer 复用**：既有 J feature 从任一 frontend 到来时 backend 改动为 0；若出现一个新 J feature，只在共享 checker/RefEval/emitter 与确有需要的 target consumer 中实现一次，不能按 frontend 或 Kernel 重写。

### 0.3 对比只做两类

- **工程对比**：Triton-centered baseline 与真实 TileLang/CUDA onboarding Git delta；这是可重放、不会虚构人工工时的主对比。
- **复用对比**：`new frontend + existing J feature` 的 backend delta 是否为 0，以及 `new J feature` 是否只实现一次。

不在本小节增加“裸 LLM/LLMLift/手写 transpiler”质量 baseline。它们主要回答恢复准确率而不是 integration-surface factorization，既会重复论文其他实验，也会消耗大量模型预算。`N×M` 只作为由真实 ownership/zero-delta 结果支持的复杂度解释，不伪造一套 pairwise compiler 的 LoC。

### 0.4 停止规则

- 本实验的跨前端运行只做 normal-J Gate1/Gate2；SCRC masked-J authority 由原 §5.2 实验负责，不在每个多前端 canary 上重复。
- fresh Codex 运行硬上限为 6 个；一个语义族得到 TileLang/CUDA 成对有效证据后立即停止，不扩成 15/84 或全量模型运行。
- 一个失败若揭示共享机制错误，只允许修共享机制并重跑该 canary；禁止添加 Kernel 名、Source path 或 case-id 分支。
- 全量集合只做无 LLM 的 registry/prepare/source-compile 审计；不能把“已注册/可编译”写成“已闭合”。
- backend 只验证 canonical J consumer，不读取 frontend、Source、π 或 case id；出现这类依赖即判复用失败。
- 最终正文最多保留 **2 张表**（onboarding；closure+lowering）和一段 failure taxonomy，其他日志进 appendix/artifact。

## 1. 这一实验真正要回答什么

论文的迁移中心主张不是“我们又支持了两个 frontend”，而是：

> **新增 Source frontend 的理解成本在 Lift 侧支付一次；只要恢复到既有 J 语义，已有 target consumer 不需要重新理解 Source。只有 J 的语义能力本身扩展时，consumer 才需要按 feature 增量实现，而不是按 frontend 或 Kernel 重写。**

因此，工程规模不应只按 frontend LoC 报告，而应拆成三个不同的增量单位：

1. **新增 Kernel，复用既有 frontend 与既有 J vocabulary**；
2. **新增 frontend syntax/realization，仍恢复为既有 J vocabulary**；
3. **新增 J semantic feature，要求共享 checker/RefEval/lowerer 或 target consumer 增量消费**。

这三个单位分别验证：

```text
per-kernel amortization
frontend-level amortization
semantic-feature-level amortization
```

它们比笼统的“接入 CUDA 用了多少行代码”更能说明 IntentIR 怎样切开原来的 `N × M` integration surface。

## 3. Research Questions

### RQ1：新增一个 Kernel 需要多少工作？

在 frontend adapter、J vocabulary 和 backend 均冻结时，加入一个新 Kernel，记录：

- production LoC；
- test LoC；
- prompt/public-context LoC；
- per-kernel rule 数量；
- 人工修改次数；
- Lift/CandidateCheck/formal Gate 调用；
- 是否无需修改 shared core 和 backend 即可 certified/lowered。

预期 headline：

```text
existing frontend + existing J feature
=> 0 production LoC, 0 per-kernel rules, 0 backend LoC
```

不能达到 0 时，必须按真实原因报告为 generic bug fix、semantic-feature extension 或 per-kernel workaround，不能全部算成“Kernel onboarding”。

### RQ2：新增一个 frontend 需要多少工作？

冻结已有 Triton-based system，分别接入 TileLang 与 CUDA，记录：

- dataset/adapter compile-run-observe LoC；
- source isolation / public frontend context LoC；
- Gate1 observer/canonicalization LoC；
- Harness binding LoC；
- shared SCRC core 修改 LoC；
- existing backend 修改 LoC；
- per-kernel rules；
- 一次接入后可覆盖的 Kernel 数量。

这里必须区分：

```text
frontend-specific production code
shared generic capability fixes
tests
generated snapshots
documentation/prompt text
```

生成的 CUDA snapshot、运行 evidence、论文文档不得计入 production onboarding LoC。

### RQ3：配对 TileLang/CUDA 的 J 哪些部分稳定，哪些差异有 Source 依据？

当前 Dataset 候选有 31 个配对 stem，其中 26 组具备双方显式 descriptor、可进入实验：

```text
tilelang:<stem>
cuda:tilelang_<stem>
```

手写 `cuda:row_sum`、`cuda:transpose2d`、`cuda:naive_gemm`、`cuda:vec_add` 不与同名或近名 TileLang case 强行配对。

配对只提供分析坐标，不是“J 必须相等”的 oracle。对每一组 independently lifted/closed artifact，比较三层关系：

1. **Layer A correspondence**：比较 tensor、op family、operand/dataflow、logical domain/index/result；报告 exact match、结构对应和真实语义差异，而不是先验要求 equality；
2. **Layer B/Interface differences**：逐项比较 predicate/fill、effect、alias/inout、output/result relation 与 ABI carrier；允许一个 frontend 使用显式 runtime extent，另一个通过 tensor shape 绑定同一维度，也允许 Source 本身造成边界差异；
3. **Authorization/Full-J differences**：单独列出 numeric/result/realization authorization 等差异，并追溯到匿名 Source/ABI/observer 事实；不用 byte digest 代替语义判断。

主要指标：

- Layer A op/dataflow/domain 的 overlap 与 exact-match rate（描述性指标，不是 pass gate）；
- Layer B difference density 与类型分布；
- source-grounded / unexplained difference rate；
- full-J exact rate（仅作诊断，预期可以很低）；
- difference 原因分类：actual Source/ABI difference / Lift error / representation ambiguity / unsupported consumer。

该比较必须是 deterministic projection/check，不创建第二份 J、不把一边修成另一边，也不按 Kernel 名写规则。每个 frontend 的闭合独立判定；跨前端比较只做事后科学分析。

### RQ4：新增 frontend 后，已有 lowerer 是否零修改复用？

从 TileLang/CUDA 恢复出的 J 交给最新 `TianchenIR-backend-certified-j-search`，按 J feature family 统计：

- accepted J 数量；
- shared `J -> Intent MLIR` materialization 成功数；
- target legality/contract projection 成功数；
- GPU/RVV lower/search 至少一条合法 state 的数量；
- frontend-specific backend LoC；
- per-kernel backend LoC。

核心判据：

```text
new frontend, existing J feature
=> backend code change = 0
```

如果 backend 需要读取 `frontend=tilelang|cuda`、Source 名称、Source path 或 π 才能 lower，则实验应判为接口复用失败，而不是成功。

### RQ5：新增 J feature 时，每个 consumer 要增加多少工作？

新 frontend 可能暴露已有 Triton corpus 未覆盖的 J feature，例如：

- new boundary predicate/fill profile；
- value/dimension relation；
- consumer-specific outside-domain identity；
- access guard / typed control；
- structured loop/carry；
- direct-store partition；
- contraction orientation/dtype；
- alias/inout/update/effect relation。

对此不应声称 backend 永远零修改。正确主张是：

> **consumer 按新的 J semantic feature 增量实现一次，而不是按每个 frontend 或每个 Kernel 重写。**

每个 feature 记录：

- schema/model LoC；
- CandidateCheck/TypeCheck LoC；
- shared FunctionalBoundary/RefEval LoC；
- shared Intent-MLIR emitter LoC；
- GPU-specific consumer LoC；
- RVV-specific consumer LoC；
- tests LoC；
- 该次增量新解锁的 frontend × Kernel 数量。

由此报告 amortization：

```text
feature implementation LoC / newly supported artifacts
```

并明确区分：

- **shared semantic consumption**：一次修改同时服务所有 target；
- **target materialization**：某 target 确实需要自己的 lowering；
- **frontend leakage**：不应存在。

## 4. 实验单位与冻结协议

### 4.1 三个增量单位

| 增量单位 | 冻结项 | 允许修改 | 预期修改范围 |
|---|---|---|---|
| New Kernel | frontend、J vocabulary、SCRC、backend | dataset case/evidence，不应有 production patch | 0 production LoC |
| New Frontend | J vocabulary、SCRC semantics、backend | adapter、compile/run/observe、public context | frontend-only |
| New J Feature | Source-independent semantic contract | schema/checker/RefEval/emitter/target capability | feature-level、非 Kernel/frontend-level |

### 4.2 冻结点

正式测量前记录三个 commit：

```text
F0: Triton-centered frontend baseline
F1: TileLang onboarding complete
F2: CUDA onboarding complete
B0: backend before consuming new frontend artifacts
B1: backend after generic J-feature additions
```

若历史 commit 无法可靠复现，不伪造人工时间。可改用：

- 真实可重放 Git diff；
- 当前代码 ownership inventory；
- controlled revert/reapply onboarding patch；
- wall-clock 自动构建/运行时间。

### 4.3 LoC 口径

统一使用一种工具（优先 `scc`，否则 `cloc`），同时报告 additions/deletions 与净增量。分类：

```text
production adapter/runtime
observer/canonicalization
public frontend context
shared schema/checker/core
shared RefEval/emitter
target-specific backend
tests
generated code (excluded from headline)
docs/evidence (excluded)
```

格式化、纯重命名、vendored/generated 文件单独列出，不混入 handwritten LoC。

### 4.4 人工工作量口径

只有在 Git/issue/agent receipt 能追溯时报告 person-hours。否则使用可重复指标：

- 修改文件数；
- handwritten LoC；
- agent model calls；
- CandidateCheck/TypeCheck/Gate rounds；
- 从冻结点到第一个 certified artifact 的 wall time；
- 从第一个到第 K 个 certified artifact 的增量时间。

LLM token/cost 是辅助指标，不作为 headline。

## 8. 判定标准与允许的负结果

论文可支持的最小结论：

1. TileLang/CUDA paired cohort 在 Layer A 呈现可量化的结构对应，同时 Layer B/ABI 差异能被 Source 事实解释；
2. 新 Kernel 在既有 vocabulary 内不需要 production/per-kernel code；
3. 新 frontend 的主要改动局限于 adapter/observer/public context；
4. 已有 backend 对恢复到既有 J feature 的新 frontend artifact 零修改消费；
5. backend 修改按新 J feature 摊销到多个 frontend/Kernel，而非出现 frontend-specific branches；
6. 至少一个 reduction 类 case 端到端展示 `TileLang/CUDA -> 对应的 Layer-A 语义与各自有依据的 Layer-B/ABI -> existing lowerer`，避免只用 add2d；
7. unsupported feature 明确列入 capability matrix，不伪装成 Lift failure或成功。

允许并应报告：

- full J bytes 因 ABI carrier/authorization 不同而不相同；
- 某些 target 暂不支持某 J feature；
- C prior 在新 target 上收益有限；
- 某些跨前端差异最终被归因为真实 Source/ABI 差异，而不是 Lift 错误。

这些结果不会破坏主张；主张是 integration cost 的因子化和摊销，不是“所有组件零代码”。

## 9. Threats to Validity

1. **历史开发过程混入通用 bug fix。** 必须给每个 diff 标注 frontend-specific、generic feature 或 cleanup。
2. **同名 Kernel 不等于同语义。** 仅使用 `origin_case_id` 配对；手写 CUDA 单独报告。
3. **LoC 易被重构放大。** 同时报文件数、净增量、handwritten additions/deletions，并排除 generated/evidence/docs。
4. **LLM 方差。** 固定 model、effort、branch/round policy；报告多次重复或至少完整调用分布。
5. **跨前端对应不等于同一个 J。** equality 从不作为闭合条件；只做 deterministic 分层比较，并把可解释差异与 Lift 错误分开。
6. **consumer unsupported 与 semantic error 混淆。** capability matrix 单独标注 Decode/TypeCheck/Gate1/Gate2/RefEval/lower 阶段。
7. **只选成功 case。** cohort 在运行前按 semantic family 锁定，所有结果进入分母。

## 11. 当前已有的部分机制 canary（不是闭合结果）

当前只有一组 same-origin `add2d` 的**部分机制证据**：

```text

```

现有 `tilelang_add2d/run-002` 中，Lift 候选通过 CandidateCheck、TypeCheck，并在固定公开 seed 的 Source-vs-J 诊断上达到 `max_abs_error=0`；但 Replay 在正式比较前失败，Gate1 未闭合、Gate2 未运行。`run-003` 被主动中断，也没有形成结果报告。现有 artifacts 中没有独立的 `cuda:tilelang_add2d` 完整闭合报告。因此，当前证据不能写成 certified pair，也不进入论文成功分母。

该 pair 的实验假设仍不是 full-J equality：Layer A 的 add/dataflow 与主要 tensor/domain 结构预计大体对应；Layer B/ABI 可能因 CUDA 的 runtime `x0` carrier 及 signed-widen authorization 出现真实差异。最终必须以两边独立的新鲜闭合工件逐项测量，不把这段预期或公开探针当正式结果。当前 canary 只说明：

- 当前 Lift 候选的 `add2d` 数学表达至少通过了一次非认证公开诊断；
- full-J byte equality 不应成为跨前端闭合条件；
- 正式结果仍需两边各自 Gate1/Gate2 闭合，再做事后 A/B 差异归因。

论文不能把这个 canary 当成功结果。执行时按冻结 cohort 依次获得 `add2d`、`row_sum`、`gather2d` 的 TileLang/CUDA 独立证据；若预注册替换条件触发，只替换确定性 unsupported 的一组，并保留原失败。

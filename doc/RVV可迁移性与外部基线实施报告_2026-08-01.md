# RVV 可迁移性与外部基线实施报告（2026-08-01）

## 1. 我们到底比较什么

RVV 没有可直接执行的 Triton Source 基线，因而不能把任意一份 C 循环都写成 “Native”，也不能把 CUDA
Triton 数字搬到 CPU 图中。本阶段把两个问题分开：

1. **可移植编译路径能做到什么**：独立、严格同边界的 C 实现交给 Clang/LLVM-RVV；
2. **成熟或专家目标实现能做到什么**：严格匹配时比较 ggml CPU/RVV 与显式 RVV intrinsic；
3. **同一份 Source 能否直接迁移**：只接受真实构建并执行的 Triton-CPU/RVV，不构造虚假 latency；
4. **IntentIR 自身打开了什么空间**：继续报告 `C-Fixed / Schedule-Only / Full` 三柱。

论文 RVV panel 因而采用以下固定名称：

| 柱子 | 含义 | 当前覆盖 |
|---|---|---:|
| LLVM-RVV C | 独立 C 语义实现，由 Clang/LLVM 迁移到 RVV；不是同源迁移 | 24/24 |
| Triton-CPU/RVV | 同一 Triton Source 经上游 CPU backend 迁移并在 RVV4 执行 | 0/24，工具链移植中 |
| Expert RVV | 独立 VLEN-agnostic intrinsic 实现 | 6/24 |
| ggml CPU/RVV | ggml 预建单线程 graph/plan 的严格同边界实现 | 4/24 |
| IntentIR Full | 同一 J 的结构与 schedule 联合搜索 winner | 24/24 可生成，逐项正式测量中 |

`Best Native RVV` 是每项适用的 Expert RVV 与 ggml CPU/RVV 中最快者，不要求所有 kernel 都有这一柱。
不存在的实现显示 N/A，而不是用分解后的近似边界补齐表格。

## 2. 当前 24 个 J 的外部覆盖

LLVM-RVV C adapter 已覆盖全部 24 项。Expert RVV 当前覆盖：

- Gather2D：动态 VL indexed gather；
- RowMask Where2D：row-hoist + 连续 RVV packet；
- TVD：RVV loss traversal 与严格同边界 gradient；
- xFormers RMSNorm：ordered vector reduction + normalization；
- LayerNorm：两次 ordered reduction + vector epilogue；
- Flash backward preprocess：FP16 dynamic-VL load、widening product 与 FP32 reduction。

ggml CPU/RVV 只接入：

- Softmax；
- xFormers RMSNorm；
- DYT；
- SwiGLU。

其余 J 包含 fused add、额外输出、特殊 predicate、custom reduction 或 ggml 不提供的公开边界，当前不把
多个 ggml primitive 的任意分解伪装成成熟库同算子。

统一 sidecar 目前会导出 34 个实现记录：24 个 LLVM-RVV C、6 个 Expert RVV、4 个 ggml CPU/RVV。

## 3. 已经暴露并修复的真实后端缺口：Gather2D

Gather2D 的 J 是明确的两级数据依赖图：

```text
take(data, row_index, axis=0)
    -> temporary[indices, width]
    -> along_axis(temporary, col_index, axis=1)
    -> output[indices]
```

此前 RVV canonical lowering 先物化完整中间行，再读取一个列元素；普通 tile/vector schedule 不能改变这个
compiler graph。Full 现在增加一个 source-name-blind 的 typed matcher，只有精确匹配上述 A 图、i32 index、
静态可整除长度和只读输入合同时才生成：

```text
output[i] = data[row_index[i], col_index[i]]
```

真实路径是：

```text
J -> Intent MLIR -> LowerGatherChainToLoops -> vector.gather
  -> LLVM masked gather -> RVV indexed load
```

它不是 Python kernel 发射。生成目标汇编已出现 `vluxei64.v`；独立 Expert RVV 使用 `vluxei32.v`，因此还保留
一个很小的 index-width 代码质量差距。

RVV4、单线程、code warm/data cold、7 batches、每 batch 16 个 cold samples 的当前结果为：

| 实现 | latency (µs) | 相对 Full |
|---|---:|---:|
| C-Fixed | 90.74 | 1.774× |
| Schedule-Only | 82.24 | 1.608× |
| IntentIR Full | 51.14 | 1.000× |
| LLVM-RVV C | 69.35 | 1.356× |
| Expert RVV | 49.46 | 0.967× |

配对交替计时中 Full 为 50.87 µs，Expert RVV 为 49.46 µs，即当前 IntentIR 达到手写 indexed intrinsic 的
97.2%。核心消融是：

```text
Schedule-Only / Full = 1.608×
```

这不是把 C 人为调差得到的结果。两根弱柱都保留 materialized implementation graph；Schedule-Only 只能在该
图上搜索 tile/vector policy。Full 才能消费 J 中的两级 gather 结构并消除中间 materialization。

## 4. 已形成作图数据的六项正式结果

当前作图子集统一使用 RVV4、单线程、code-warm/data-cold、7 个交替批次与 natural workload。下表的
`G_schedule = C-Fixed / Schedule-Only`，`G_full = Schedule-Only / Full`；外部列使用与 Full 交替配对后的
`external / Full`，因此大于 1 表示 IntentIR 更快。

| Kernel | C-Fixed (µs) | Schedule-Only (µs) | Full (µs) | G_schedule | G_full | LLVM-RVV C / Full | Best Native / Full |
|---|---:|---:|---:|---:|---:|---:|---:|
| Gather2D | 90.74 | 82.24 | 51.14 | 1.103× | 1.608× | 1.387× | 0.972× Expert |
| RowMask Where2D | 6143.11 | 6088.01 | 6088.01 | 1.009× | 1.000× | 0.983× | 0.982× Expert |
| TVD | 494062.57 | 301694.86 | 46255.39 | 1.638× | 6.522× | 0.971× | 0.954× Expert |
| Softmax | 493062.53 | 311769.56 | 31646.82 | 1.581× | 9.852× | 7.599× | 1.617× ggml |
| xFormers RMSNorm | 2492980.84 | 527097.38 | 107831.15 | 4.730× | 4.888× | 1.647× | 1.109× Expert |
| Flash backward preprocess | 1913189.67 | 1286453.22 | 44713.90 | 1.487× | 28.771× | 2.490× | 1.634× Expert |

这六项上的几何平均 `G_schedule=1.651×`、`G_full=4.940×`。相对逐项最快 Expert/ggml，IntentIR 的配对
几何平均为 1.178×；同时保留 Gather、RowMask、TVD 三个尚未超过 Expert 的负例，而不是只画胜出的 kernel。

TVD 暴露了另一类可复用缺口。旧 Full 已经分别融合 loss 与 gradient 各自的 producer 链，但两个公开
输出仍各自遍历完整输入，所以 `a/b` 被读取两遍。新增的 `FuseLinalgSiblingOutputs` 按 all-parallel iterator、
indexing map、write-only output 和返回值 use 精确匹配，把共享输入的两个 elementwise roots 合成一个
multi-output `linalg.generic`。它保持每个标量表达式的操作顺序，不做数值放宽。

正式结果中 Full/Schedule 达到 6.522×；所有两个输出均通过同一 Q。Full 达到 Expert RVV 的 95.4%。这说明
收益不是来自“打开 fusion pass”这个名字，而是 J 的多输出数据流让后端识别出共享输入遍历，
搜索到固定 implementation graph 的 retile 无法产生的新 multi-output loop。

Softmax 的 Full 是一条真正的 MLIR vector path：输入最大值、范围缩减多项式 exp、归一化 reduction 和输出在
一个 row program 内完成，消除多次 tensor materialization。该执行域候选在所有输出元素上按 J 的 Q/D 比较，
当前最大绝对误差为 `2.21e-9`。它相对 ggml CPU/RVV 为 1.617×，相对 LLVM-RVV C 为 7.599×。

Flash backward preprocess 则消费 J 中显式的 FP16 输入、FP32 cast/mul、最后一维 reduction 与 FP32 输出，新增
`VectorizeLinalgMixedPrecisionDotReduction`。目标代码是一条 dynamic-VL widening-dot path，出现
`vfwmul.vv` 与 RVV vector reduction；9 个物化算子收敛为 1 个 loop nest。它使 Full/Schedule 达到
28.771×，并相对独立 Expert RVV 达到 1.634×。这不是 Python 发射，也不是把 benchmark 名写进 lowerer。

xFormers RMSNorm 的 Full 已超过独立 Expert RVV。ggml adapter 构造公开边界完全一致的 `rms_norm + mul` graph，graph 与
single-thread compute plan 在计时外建立，计时内只更新外部 tensor pointer 并执行 graph。

RVV4 的 Clang 17 无法编译上游 ggml RISC-V quant 文件使用的新 tuple intrinsic API。当前外部构建只为链接完整
性把未参与本实验的 quant/repack 符号退回 generic fallback；RMSNorm、Softmax 等浮点路径仍以
`rv64gcv_zfh_zvfh` 编译，并确实包含 RVV intrinsic。论文名称因此使用 **ggml CPU/RVV**，不写成“完整 ggml
量化 RVV backend”。

该工具链兼容补丁保存在
`tools/rvv_external_patches/llama_cpp_rvv_float_clang17.patch`；它不修改参与比较的浮点算子定义，只排除未参与
实验且无法由 Clang 17 编译的 quant fast path，并为动态库补齐 generic fallback 符号。

## 5. Triton-CPU/RVV 的真实边界

上游 Triton-CPU 当前是实验性 CPU backend，没有 riscv64 预编译 LLVM/MLIR 包。其默认代码路径还包含：

- x86-only nanokernel lowering；
- AVX/SSE/NEON vector-library 判定；
- 默认 GPU backend/toolchain 下载；
- riscv64 不存在的预编译 LLVM artifact。

已经完成的移植探针是：只保留 CPU backend、关闭 GPU 工具链下载，并在 RVV4 上进入真实 CMake 配置。系统
LLVM 17 缺少 MLIR 开发包，也不满足当前 Triton 锁定的 LLVM API。当前正在 RVV4 上构建 Triton 指定提交的
LLVM/MLIR，仅启用 RISCV target；构建完成后用同一 Triton vector-add/elementwise Source 真实编译、加载并执行。
只有它通过相同输出比较，才会增加
`Triton-CPU/RVV` 柱；否则结论是当前上游路径不支持，而不是给它估算数字。

CPU-only 与非 x86 portability probe 的最小补丁保存在
`tools/rvv_external_patches/triton_cpu_riscv_probe.patch`：只关闭无关 GPU backend、x86 nanokernel 和未被 RVV
选择却被无条件链接的 SLEEF，不替换 Triton 的 IR 或代码生成器。

## 6. 可直接作图的数据接口

多基线 runner 对每个外部实现执行：

1. 相同输入 payload；
2. 所有 observable outputs 的同一比较策略；
3. 与 Full 交替配对的 cold-data 计时；
4. 单线程与相同 affinity；
5. 每项记录 measured、failed 或 N/A。

`tools/export_rvv_figure_table.py` 把一个或多个无重复 kernel 的 report 转为：

- long-form CSV：一行一个真实可画柱；
- JSON：wide rows、measured bars 和 failed/N/A coverage；
- `full_speedup_vs_bar = bar_latency / full_latency`；
- paired Full 与 external speedup 原样保留。

因此作图阶段不再手工挑数，也不会因某个外部实现不适用而丢掉 kernel。
